# One-job company application flow

The private browser pilot now selects native or company-site Naukri listings. Company navigation starts only from the selected listing's exact `Apply on company site` control after job/company verification. Public HTTPS and DNS checks remain active. The bounded handoff can follow up to five new origins for 20 seconds. Subsequent automation stays on those origins or recognized embedded ATS providers (Greenhouse, Lever, Ashby, Workable, Workday). Password/OTP/CAPTCHA challenges pause; they are not solved or bypassed.

The employer destination must corroborate the selected title and company before any profile details or resume are entered. A resume uploaded on Naukri is not proof of upload to the employer: the employer form requires a separate attachment. Multiple steps and popup forms remain in the same task; unknown required answers pause with current-field validation. Hidden old controls have their previous agent IDs cleared before each observation, preventing duplicate IDs after step changes. Ambiguous submissions remain UNKNOWN and are never automatically repeated.

For dashboard receipts, configure the same private 64-hex `PRIVATE_BROWSER_CALLBACK_KEY` on the API and browser helper. The helper signs the receipt and calls `/profile/browser-receipt` directly using the user's existing authenticated request. This route is not exposed by the frontend proxy. The API verifies raw-body HMAC, authenticated owner, five-minute signature age and employer receipt format, then upserts one `JobApplication` using the task UUID. Repeated receipt saving does not add applications or replay submission. No new database table is needed. Failed receipt storage can be retried via Refresh task. Preserve this key outside Git.

Testing: backend build, `node --test scripts/company-navigation.test.cjs scripts/browser-receipt.test.cjs scripts/naukri-workflow.test.cjs scripts/naukri-discovery.test.cjs`. Fixtures cover same-tab/popup/embedded forms, actual file attachment, unknown answers and resumed submission, mismatched employers, private destinations and signed idempotent recording. Fixture receipts are not real applications. A real employer receipt is still required before claiming a real job applied.

This is a bounded one-job pilot, not support for every arbitrary employer UI. Custom widgets, site blocks, unsupported redirects, account questions or unverifiable identity can still require input. Local execution stops if the PC/helper stops; 24/7 hosting is a separate deployment. WhatsApp is a separately configured channel; this pilot currently shows required questions in its website dialog.

Generic employer homepages are searched read-only through up to three actual same-origin careers/job links. No candidate information is entered until both employer and selected job are verified. Automatic selection can skip two company destinations without a matching form and inspect a third eligible listing; it never retries a submission. New company tabs with no opener are supported and stale company tabs are excluded from later handoffs.

Live validation on 2026-11-16: Naukri confirmed the original resume upload. Flashoot handed off to its generic homepage and Fresha to general careers, without a verified matching application form. Neither was counted as sent. Local API health, database-backed pricing and frontend pricing proxy returned 200; unauthenticated private endpoints returned 401. Backend and frontend builds passed. No real employer application confirmation was obtained in this validation.

Further live validation reached Magzest Consultancy Services' Frontend Developer application. The bot filled the original resume's name/email, selected the exact advertised position, attached `Jainoddin_Shaik_Resume.pdf`, and clicked Submit Application once. The employer's form first displayed Sending, then explicitly reported: "Something went wrong sending your application. Please email your resume directly to contact@magzest.tech." This attempt is FAILED, not APPLIED; no email fallback was sent. Delayed errors/confirmations can be inspected on status refresh without replaying submission.

After the user explicitly requested a different company and renewed the private login, a separate ProdEX Technologies Frontend Developer application completed on 2026-11-16 at 18:09:25 UTC. The original PDF was attached, required saved facts were filled, and one submission navigated to `https://www.prodex.in/careers/thanks/`, displaying `THANK YOU FOR APPLYING!`. The signed receipt was saved and independently checked in the database as APPLIED for ProdEX Technologies. The masked confirmation screenshot is `output/applied-prodex.jpg` in the workspace. This is one confirmed portal submission, not a hiring outcome or proof that every employer form is supported.

On the user's next explicit one-job request, DataSpeaks was skipped before submission because it requested verification. The same 70% threshold was retained while searching React/Next.js roles supported by the resume. Ratnam Solutions' React js Developer application was then submitted once through native Naukri Apply. Its `/myapply/saveApply` page displayed `Applied to "React js Developer"`; the signed receipt was independently checked as APPLIED in the database. Screenshot: `output/applied-ratnam-solutions.jpg`. The receipt detector now supports exact quoted Applied-to messages in plain div/span elements only on that Naukri result path, and rejects mismatched titles or origins. A delayed confirmation refresh records the result without clicking Apply again.

Fixes from this validation: bind observed company popups to the bounded handoff even if initial navigation was not intercepted; accept job headings in h3; isolate a unique resume/application form from unrelated newsletter/consultation forms; choose an exact advertised position deterministically; attach the original resume before planning; submit complete verified application forms without overwriting already selected position fields. Job discovery prefers suitable direct Naukri applications before falling back to company entries. These fixes do not guarantee employer delivery or bypass verification challenges.
